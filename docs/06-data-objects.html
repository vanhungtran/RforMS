5  Construct Analysis-Ready Data Objects

  • Show All Code
  • Hide All Code
  • View Source

The difference between an afternoon of frustration and a clean analysis is almost always the object you put your data in. The same MS data can live as a pile of files, a flat matrix, or a linked hierarchy of peptides and proteins — and choosing wrong means fighting your tools at every step. This chapter introduces the four Bioconductor containers that hold MS data and, more importantly, teaches you when to reach for each.

WarningThe One Mistake to Avoid

Flattening a QFeatures hierarchy into a bare matrix too early. Once you drop the peptide-to-protein links, you can no longer trace a result back or re-aggregate it. Keep the linked object until the very last step.

5.1 Learning Objectives

By the end of this chapter, you will be able to:

  • Construct and inspect Spectra objects and choose the right backend for your data size
  • Link raw spectra to sample metadata using MsExperiment
  • Build a SummarizedExperiment for feature-by-sample intensity data
  • Organise quantitative proteomics data in a QFeatures hierarchy (spectra -> peptides -> proteins)
  • Convert between data representations and export objects for downstream analysis

5.2 Analysis Environment

Chapter 2 introduced the package ecosystem and Chapter 3 described project-level reproducibility. Here we assume the core packages are installed and focus on object construction rather than package setup.

Code

5.3 Understanding the R for Mass Spectrometry Ecosystem

5.3.1 2.1 Package Architecture

The R for Mass Spectrometry initiative follows a modular, backend-based architecture:

User workflows
  Preprocessing -> feature detection -> statistics -> visualisation
        |
High-level packages
  QFeatures | xcms | PSMatch | MetaboCoreUtils
        |
Core data structure
  Spectra
        |
Backends
  MsBackendMzR | MsBackendHdf5Peaks | MsBackendSql | ...

Key concept: The Spectra object separates data manipulation logic from data storage. Backends handle file I/O and memory management, allowing you to switch between in-memory, on-disk, or database storage without changing analysis code.

Code 
library(tibble)
# Available backends and their use cases
backend_info <- tibble(
  Backend = c("MsBackendMzR", "MsBackendDataFrame", 
              "MsBackendHdf5Peaks", "MsBackendSql"),
  Storage = c("File (mzML/mzXML)", "RAM", "HDF5", "SQL Database"),
  Best_For = c("Raw data reading", "Small datasets (< 1000 spectra)", 
               "Large datasets (10k-1M spectra)", "Multi-user/collaborative"),
  Memory_Usage = c("Low", "High", "Medium", "Low")
)

print(backend_info)

5.3.2 Choosing the Right Backend

The backend you choose determines memory footprint, access speed, and scalability. Here is a decision guide:

Scenario Recommended Backend Reason
A few small mzML files, interactive exploration MsBackendMzR Simple, no extra dependencies; reads directly from raw files
Thousands of spectra, need fast random access MsBackendHdf5Peaks Stores peak data in HDF5; lazy loading; much faster than re-parsing mzML
Multi-user lab, shared data, complex metadata queries MsBackendSql Stores spectra + metadata in a relational database; supports SQL queries across experiments
Small synthetic or processed spectra in memory MsBackendDataFrame Good for testing and small result sets; everything in RAM
Public repository data (MetaboLights, MassIVE) MsBackendMassIVE or MsBackendMetaboLights Direct access to deposited datasets without downloading (Chapter 16 covers MsBackendMetaboLights in the metabolomics workflow)
Proteomics repository data (PRIDE) rpx Queries PRIDE and returns Spectra objects from deposited identifications (Chapter 29 covers rpx in the reproducible reporting workflow)

General rule: Use MsBackendMzR for initial exploration of a few files. Switch to MsBackendHdf5Peaks when your experiment grows beyond 10–20 runs or when loading times become noticeable. Reach for MsBackendSql when multiple people need to query the same data with different filters.

Code 
# Converting between backends
ms_data_hdf5 <- setBackend(ms_data, MsBackendHdf5Peaks())

5.3.3 Why This Architecture Matters for MS Data

Mass spectrometry data presents unique challenges: - Large file sizes: Single runs can be 1-10 GB - Variable structure: MS1 vs MS2 spectra, profile vs centroid data - Complex metadata: Instrument parameters, sample information, processing history

The backend system addresses these by: 1. Lazy evaluation: Data is only loaded when needed 2. Pluggable storage: Same code works for 100 or 1 million spectra 3. Consistent interface: Switch backends with one line of code

5.4 Core Data Structures for MS Data

5.4.1 Vectors and Matrices

Mass spectra are fundamentally collections of (m/z, intensity) pairs, which map naturally to R’s vector and matrix structures.

Code 
# Example: Creating a simple spectrum with 5 peaks
mz_values <- c(104.10, 205.20, 306.30, 407.40, 508.50)
intensity_values <- c(1200, 3500, 8900, 2100, 450)

# Option 1: Separate vectors (common for processing)
cat("Spectrum as separate vectors:\n")
cat("  m/z:", paste(mz_values, collapse = ", "), "\n")
cat("  intensities:", paste(intensity_values, collapse = ", "), "\n\n")

# Option 2: Matrix (efficient for computation)
spectrum_matrix <- cbind(mz = mz_values, intensity = intensity_values)
cat("Spectrum as matrix (nrow =", nrow(spectrum_matrix), "):\n")
print(head(spectrum_matrix))

# Option 3: Data frame (good for adding metadata)
spectrum_df <- data.frame(
  mz = mz_values,
  intensity = intensity_values,
  relative_intensity = intensity_values / max(intensity_values) * 100
)

5.4.4 The Split-Apply-Combine Pattern for MS Data

This is the single most common pattern in MS data analysis: split data by a grouping variable, apply a computation to each group, and combine the results. In tidyverse, this is group_by() + summarise():

Code 
# Compute per-sample summary statistics from a feature matrix
feature_df |>
  pivot_longer(-feature_id, names_to = "sample", values_to = "intensity") |>
  group_by(sample) |>
  summarise(
    n_features    = n(),
    n_missing     = sum(is.na(intensity)),
    median_log2   = median(log2(intensity + 1), na.rm = TRUE),
    cv_pct        = sd(intensity, na.rm = TRUE) / mean(intensity, na.rm = TRUE) * 100,
    .groups       = "drop"
  )

This pattern appears in every chapter: QC metrics per sample, missingness rates per feature, CV in QC pools, differential testing per protein. Master it early.

5.4.5 Joins: Merging MS Metadata with Results

MS data analysis constantly merges tables: metadata ↔︎ feature matrices, identification results ↔︎ quantification tables, protein annotations ↔︎ DE results. Use the *_join() family — never base R merge():

Code 
# left_join: keep all rows from the left table
de_results |>
  left_join(protein_annotations, by = "protein_id")

# anti_join: find features in one table but not the other (QC check)
features_in_matrix_only <- anti_join(
  feature_ids_from_matrix,
  feature_ids_from_metadata,
  by = "feature_id"
)

Rule of thumb for joins in MS workflows: | Join | Use Case | |——|———-| | left_join() | Add annotations to results (keep all results) | | inner_join() | Keep only rows present in both tables | | anti_join() | QC — find mismatches between metadata and data | | full_join() | Merge two feature tables with different coverage |

5.5.2 Reading MS Data with Spectra

Code 
# Load example data from the msdata package
library(msdata)

# Get path to example proteomics file (mzML format)
proteomics_files <- msdata::proteomics(full.names = TRUE)
# proteomics_files[1] is an SRM/MRM standard-mix file (targeted transitions,
# not full spectra) and will not load through Spectra(); pick a full-scan
# DDA file instead (see Chapter 4 for the acquisition-mode distinction).
ms_file <- grep("MS3TMT", proteomics_files, value = TRUE)[1]
cat("Example file:", basename(ms_file), "\n")
cat("File size:", round(file.info(ms_file)$size / 1e6, 2), "MB\n")

# Method 1: Read with automatic backend selection
ms_data <- Spectra(ms_file)

# Method 2: Explicitly specify backend (recommended for reproducibility)
ms_data <- Spectra(ms_file, backend = MsBackendMzR())

# Basic exploration
cat("\n=== Dataset Summary ===\n")
cat(sprintf("Total spectra:   %d\n", length(ms_data)))
cat(sprintf("MS levels:       %s\n", 
            paste(unique(msLevel(ms_data)), collapse = ", ")))
cat(sprintf("Retention time:  %.1f - %.1f seconds (%.2f - %.2f min)\n",
            min(rtime(ms_data)), max(rtime(ms_data)),
            min(rtime(ms_data))/60, max(rtime(ms_data))/60))
cat(sprintf("Polarity:        %s\n", 
            ifelse(all(polarity(ms_data) == 1), "Positive", "Negative")))

5.5.3 Working with Spectral Data

Code 
# Access specific spectra
first_spectrum <- ms_data[1]
cat(sprintf("Spectrum 1: MS level %d at RT = %.2f sec\n",
            msLevel(first_spectrum), rtime(first_spectrum)))

# Extract peak data
peaks <- peaksData(first_spectrum)[[1]]  # Returns [mz, intensity] matrix
colnames(peaks) <- c("mz", "intensity")

cat(sprintf("\nPeak information:\n"))

cat(sprintf("  m/z range:        %.2f - %.2f\n", min(peaks[,1]), max(peaks[,1])))
cat(sprintf("  Intensity range:  %.2e - %.2e\n", min(peaks[,2]), max(peaks[,2])))

# Find top 5 most intense peaks
top_peaks <- peaks[order(peaks[,2], decreasing = TRUE)[1:5], ]
cat("\nTop 5 most intense peaks:\n")
print(top_peaks)

# Filtering spectra
ms2_spectra <- filterMsLevel(ms_data, 2L)
cat(sprintf("\nFiltered to %d MS2 spectra (%.1f%% of total)\n",
            length(ms2_spectra), length(ms2_spectra)/length(ms_data)*100))

# RT filtering: first 10 minutes only
early_spectra <- filterRt(ms_data, rt = c(0, 600))
cat(sprintf("Spectra in first 10 min: %d\n", length(early_spectra)))

5.5.4 Exporting Data

Code 
# Export subsets to different formats

# Export first 100 spectra as new mzML file

# Export MS2 spectra to MGF for database searching

  as.data.frame() %>%

  colnames(peaks) <- c("mz", "intensity")
  peaks
})
saveRDS(peak_lists, "peak_lists.rds")

5.6 The Other Three Containers: MsExperiment, SummarizedExperiment, QFeatures

Spectra handles one job well: a collection of scans. Real experiments need more than that — sample metadata that stays locked to the right raw files, a feature-by-sample matrix with row and column annotations, and (for bottom-up proteomics) a multi-level PSM-to-protein hierarchy that keeps every aggregation step traceable. This is what MsExperiment, SummarizedExperiment, and QFeatures are for.

5.6.1 Linking Files to Sample Metadata: MsExperiment

A Spectra object on its own has no concept of “sample” — it is just scans. The moment you have more than one file, you need something that keeps each file paired with its condition, batch, and injection order, so that a re-ordering or a dropped file cannot silently desynchronise data from metadata. MsExperiment does exactly this: it wraps a Spectra object together with a sampleData table and guarantees the two stay linked.

Code 
library(MsExperiment)

# Link the two full-scan TMT files to a sample metadata table
tmt_files <- grep("MS3TMT", proteomics_files, value = TRUE)
sample_tbl <- data.frame(
  sample_name     = basename(tmt_files),
  condition       = c("TMT_run_A", "TMT_run_B"),
  injection_order = 1:2
)

mse <- readMsExperiment(spectraFiles = tmt_files, sampleData = sample_tbl)
mse
sampleData(mse)

# The underlying Spectra object is always reachable
length(spectra(mse))

The payoff shows up the moment you subset: mse[mse$condition == "TMT_run_A"] carries both the matching spectra and the matching metadata row along together, whereas keeping a Spectra object and a data.frame as two separate variables leaves you responsible for keeping their row order in sync by hand.

5.6.2 Building a SummarizedExperiment from a Feature Matrix

Once raw spectra have been reduced to a feature-by-sample intensity matrix (Chapter 7 shows how), SummarizedExperiment is the container that carries that matrix alongside feature-level annotation (rowData) and sample-level annotation (colData) as one synchronised object.

Code 
library(SummarizedExperiment)

set.seed(1)
protein_mat <- matrix(
  rnorm(24, mean = 20, sd = 2), nrow = 6, ncol = 4,
  dimnames = list(paste0("protein_", 1:6), paste0("sample_", 1:4))
)

row_meta <- DataFrame(gene_symbol = paste0("GENE", 1:6), n_peptides = c(5, 3, 8, 2, 6, 4))
col_meta <- DataFrame(condition = rep(c("control", "treated"), each = 2), batch = rep(c("A", "B"), 2))

se <- SummarizedExperiment(
  assays  = list(intensity = protein_mat),
  rowData = row_meta,
  colData = col_meta
)
se

5.6.4 Converting Between Representations

The four containers are not disconnected — each is built from the ones before it, and you rarely need to serialize data to a bare matrix to move between them.

Code 
# Every QFeatures assay is itself a SummarizedExperiment
class(feat1[["peptides"]])
[1] "SummarizedExperiment"
attr(,"package")
[1] "SummarizedExperiment"
Code 
is(feat1[["peptides"]], "SummarizedExperiment")
[1] TRUE
Code 
# Pull one level out as a standalone SummarizedExperiment — useful when a
# function (e.g., a limma workflow) expects that class directly
peptide_se <- feat1[["peptides"]]
Code 
# MsExperiment carries its Spectra object internally — pull it out for any
# function that expects a plain Spectra object
sps <- spectra(mse)

Choosing a container:

You have… Reach for…
Raw scans from one or more files, no sample structure yet Spectra
Multiple raw files that must stay paired with sample metadata MsExperiment
A finished feature-by-sample matrix (metabolomics, or one level of proteomics) SummarizedExperiment
A PSM-to-protein hierarchy that must stay traceable across aggregation QFeatures

5.7.1 Memory Management

Code 
# Check memory usage of Spectra object
object.size(ms_data) / 1e6  # Size in MB

# Convert to memory-efficient backend for large datasets
ms_data_hdf5 <- setBackend(ms_data, backend = MsBackendHdf5Peaks())

# Remove large objects when no longer needed

5.7.2 Common Issues and Solutions

Issue Symptom Solution
mzR compilation fails Error installing MsBackendMzR Install system dependencies: libnetcdf-dev, libxml2-dev
Out of memory R crashes or slows down Use HDF5 or SQL backend instead of in-memory
Slow file reading Spectra() takes minutes Use backend = MsBackendHdf5Peaks() for faster access
Missing precursor info precursorMz returns NA Check if file contains MS2 spectra with any(msLevel(ms_data) == 2)

# Construct Analysis-Ready Data Objects

The difference between an afternoon of frustration and a clean analysis is almost always the object you put your data in. The same MS data can live as a pile of files, a flat matrix, or a linked hierarchy of peptides and proteins — and choosing wrong means fighting your tools at every step. This chapter introduces the four Bioconductor containers that hold MS data and, more importantly, teaches you when to reach for each.

::: {.callout-warning title="The One Mistake to Avoid"}
Flattening a `QFeatures` hierarchy into a bare matrix too early. Once you drop the peptide-to-protein links, you can no longer trace a result back or re-aggregate it. Keep the linked object until the very last step.
:::

## Understanding the R for Mass Spectrometry Ecosystem

### 2.1 Package Architecture

The R for Mass Spectrometry initiative follows a **modular, backend-based architecture**:

```text
User workflows
  Preprocessing -> feature detection -> statistics -> visualisation
        |
High-level packages
  QFeatures | xcms | PSMatch | MetaboCoreUtils
        |
Core data structure
  Spectra
        |
Backends
  MsBackendMzR | MsBackendHdf5Peaks | MsBackendSql | ...
```

**Key concept**: The `Spectra` object separates **data manipulation logic** from **data storage**. Backends handle file I/O and memory management, allowing you to switch between in-memory, on-disk, or database storage without changing analysis code.

```{r}
library(tibble)
# Available backends and their use cases
backend_info <- tibble(
  Backend = c("MsBackendMzR", "MsBackendDataFrame", 
              "MsBackendHdf5Peaks", "MsBackendSql"),
  Storage = c("File (mzML/mzXML)", "RAM", "HDF5", "SQL Database"),
  Best_For = c("Raw data reading", "Small datasets (< 1000 spectra)", 
               "Large datasets (10k-1M spectra)", "Multi-user/collaborative"),
  Memory_Usage = c("Low", "High", "Medium", "Low")
)

print(backend_info)
```

### Choosing the Right Backend

The backend you choose determines memory footprint, access speed, and scalability. Here is a decision guide:

| Scenario | Recommended Backend | Reason |
|----------|-------------------|--------|
| A few small mzML files, interactive exploration | `MsBackendMzR` | Simple, no extra dependencies; reads directly from raw files |
| Thousands of spectra, need fast random access | `MsBackendHdf5Peaks` | Stores peak data in HDF5; lazy loading; much faster than re-parsing mzML |
| Multi-user lab, shared data, complex metadata queries | `MsBackendSql` | Stores spectra + metadata in a relational database; supports SQL queries across experiments |
| Small synthetic or processed spectra in memory | `MsBackendDataFrame` | Good for testing and small result sets; everything in RAM |
| Public repository data (MetaboLights, MassIVE) | `MsBackendMassIVE` or `MsBackendMetaboLights` | Direct access to deposited datasets without downloading (Chapter 16 covers `MsBackendMetaboLights` in the metabolomics workflow) |
| Proteomics repository data (PRIDE) | `rpx` | Queries PRIDE and returns `Spectra` objects from deposited identifications (Chapter 29 covers `rpx` in the reproducible reporting workflow) |

**General rule**: Use `MsBackendMzR` for initial exploration of a few files. Switch to `MsBackendHdf5Peaks` when your experiment grows beyond 10–20 runs or when loading times become noticeable. Reach for `MsBackendSql` when multiple people need to query the same data with different filters.

```{r}
#| eval: false
# Converting between backends
ms_data_hdf5 <- setBackend(ms_data, MsBackendHdf5Peaks())
```

### Why This Architecture Matters for MS Data

Mass spectrometry data presents unique challenges:
- **Large file sizes**: Single runs can be 1-10 GB
- **Variable structure**: MS1 vs MS2 spectra, profile vs centroid data
- **Complex metadata**: Instrument parameters, sample information, processing history

The backend system addresses these by:
1. **Lazy evaluation**: Data is only loaded when needed
2. **Pluggable storage**: Same code works for 100 or 1 million spectra
3. **Consistent interface**: Switch backends with one line of code

## Core Data Structures for MS Data

### Vectors and Matrices

Mass spectra are fundamentally collections of **(m/z, intensity)** pairs, which map naturally to R's vector and matrix structures.

```{r}
#| eval: false
# Example: Creating a simple spectrum with 5 peaks
mz_values <- c(104.10, 205.20, 306.30, 407.40, 508.50)
intensity_values <- c(1200, 3500, 8900, 2100, 450)

# Option 1: Separate vectors (common for processing)
cat("Spectrum as separate vectors:\n")
cat("  m/z:", paste(mz_values, collapse = ", "), "\n")
cat("  intensities:", paste(intensity_values, collapse = ", "), "\n\n")

# Option 2: Matrix (efficient for computation)
spectrum_matrix <- cbind(mz = mz_values, intensity = intensity_values)
cat("Spectrum as matrix (nrow =", nrow(spectrum_matrix), "):\n")
print(head(spectrum_matrix))

# Option 3: Data frame (good for adding metadata)
spectrum_df <- data.frame(
  mz = mz_values,
  intensity = intensity_values,
  relative_intensity = intensity_values / max(intensity_values) * 100
)
```

### The Split-Apply-Combine Pattern for MS Data

This is the single most common pattern in MS data analysis: split data by a grouping variable, apply a computation to each group, and combine the results. In tidyverse, this is `group_by()` + `summarise()`:

```{r}
#| eval: false
# Compute per-sample summary statistics from a feature matrix
feature_df |>
  pivot_longer(-feature_id, names_to = "sample", values_to = "intensity") |>
  group_by(sample) |>
  summarise(
    n_features    = n(),
    n_missing     = sum(is.na(intensity)),
    median_log2   = median(log2(intensity + 1), na.rm = TRUE),
    cv_pct        = sd(intensity, na.rm = TRUE) / mean(intensity, na.rm = TRUE) * 100,
    .groups       = "drop"
  )
```

This pattern appears in every chapter: QC metrics per sample, missingness rates per feature, CV in QC pools, differential testing per protein. Master it early.

### Joins: Merging MS Metadata with Results

MS data analysis constantly merges tables: metadata ↔ feature matrices, identification results ↔ quantification tables, protein annotations ↔ DE results. Use the `*_join()` family — never base R `merge()`:

```{r}
#| eval: false
# left_join: keep all rows from the left table
de_results |>
  left_join(protein_annotations, by = "protein_id")

# anti_join: find features in one table but not the other (QC check)
features_in_matrix_only <- anti_join(
  feature_ids_from_matrix,
  feature_ids_from_metadata,
  by = "feature_id"
)
```

**Rule of thumb for joins in MS workflows:**
| Join | Use Case |
|------|----------|
| `left_join()` | Add annotations to results (keep all results) |
| `inner_join()` | Keep only rows present in both tables |
| `anti_join()` | QC — find mismatches between metadata and data |
| `full_join()` | Merge two feature tables with different coverage |

## The Other Three Containers: MsExperiment, SummarizedExperiment, QFeatures

`Spectra` handles one job well: a collection of scans. Real experiments need more than that — sample metadata that stays locked to the right raw files, a feature-by-sample matrix with row and column annotations, and (for bottom-up proteomics) a multi-level PSM-to-protein hierarchy that keeps every aggregation step traceable. This is what `MsExperiment`, `SummarizedExperiment`, and `QFeatures` are for.

### Linking Files to Sample Metadata: MsExperiment

A `Spectra` object on its own has no concept of "sample" — it is just scans. The moment you have more than one file, you need something that keeps each file paired with its condition, batch, and injection order, so that a re-ordering or a dropped file cannot silently desynchronise data from metadata. `MsExperiment` does exactly this: it wraps a `Spectra` object together with a `sampleData` table and guarantees the two stay linked.

```{r}
#| eval: false
library(MsExperiment)

# Link the two full-scan TMT files to a sample metadata table
tmt_files <- grep("MS3TMT", proteomics_files, value = TRUE)
sample_tbl <- data.frame(
  sample_name     = basename(tmt_files),
  condition       = c("TMT_run_A", "TMT_run_B"),
  injection_order = 1:2
)

mse <- readMsExperiment(spectraFiles = tmt_files, sampleData = sample_tbl)
mse
sampleData(mse)

# The underlying Spectra object is always reachable
length(spectra(mse))
```

The payoff shows up the moment you subset: `mse[mse$condition == "TMT_run_A"]` carries both the matching spectra and the matching metadata row along together, whereas keeping a `Spectra` object and a `data.frame` as two separate variables leaves you responsible for keeping their row order in sync by hand.

### Building a SummarizedExperiment from a Feature Matrix

Once raw spectra have been reduced to a feature-by-sample intensity matrix (Chapter 7 shows how), `SummarizedExperiment` is the container that carries that matrix alongside feature-level annotation (`rowData`) and sample-level annotation (`colData`) as one synchronised object.

```{r}
library(SummarizedExperiment)

set.seed(1)
protein_mat <- matrix(
  rnorm(24, mean = 20, sd = 2), nrow = 6, ncol = 4,
  dimnames = list(paste0("protein_", 1:6), paste0("sample_", 1:4))
)

row_meta <- DataFrame(gene_symbol = paste0("GENE", 1:6), n_peptides = c(5, 3, 8, 2, 6, 4))
col_meta <- DataFrame(condition = rep(c("control", "treated"), each = 2), batch = rep(c("A", "B"), 2))

se <- SummarizedExperiment(
  assays  = list(intensity = protein_mat),
  rowData = row_meta,
  colData = col_meta
)
se
```

The three pieces move together under a single set of accessors, and subsetting by either dimension keeps them aligned automatically:

```{r}
assay(se)          # the intensity matrix
rowData(se)         # feature annotation
colData(se)         # sample annotation

# Subset by sample metadata — rowData travels along unchanged
assay(se[, se$condition == "treated"])

# Subset by feature annotation — colData travels along unchanged
assay(se[rowData(se)$n_peptides >= 5, ])
```

This is the object every downstream statistical chapter expects: `limma` (Chapter 20), `variancePartition` (Chapter 21), and the machine-learning workflows in Chapter 22 all take a feature-by-sample matrix with this exact shape.

### Assembling a QFeatures Hierarchy

Bottom-up proteomics measures PSMs, not proteins. `QFeatures` keeps the PSM -> peptide -> protein aggregation path intact and auditable, storing each level as its own assay while tracking how rows at one level map to rows at the next.

```{r}
library(QFeatures)

data(feat1, package = "QFeatures")
feat1
colData(feat1)
assay(feat1[["psms"]])
```

`aggregateFeatures()` collapses one level into the next using a grouping column and a summary function, producing a new assay while leaving the original intact:

```{r}
feat1 <- aggregateFeatures(feat1, i = "psms", fcol = "Sequence", name = "peptides", fun = colMeans)
assay(feat1[["peptides"]])
```

This chapter stops at construction. Chapter 12 picks up from here for the full workflow — filtering contaminants, normalizing, aggregating peptides to proteins, and diagnosing the result with PCA — using the same `aggregateFeatures()` mechanics shown above.

### Converting Between Representations

The four containers are not disconnected — each is built from the ones before it, and you rarely need to serialize data to a bare matrix to move between them.

```{r}
# Every QFeatures assay is itself a SummarizedExperiment
class(feat1[["peptides"]])
is(feat1[["peptides"]], "SummarizedExperiment")

# Pull one level out as a standalone SummarizedExperiment — useful when a
# function (e.g., a limma workflow) expects that class directly
peptide_se <- feat1[["peptides"]]
```

```{r}
#| eval: false
# MsExperiment carries its Spectra object internally — pull it out for any
# function that expects a plain Spectra object
sps <- spectra(mse)
class(sps)
```

**Choosing a container:**

| You have... | Reach for... |
|---|---|
| Raw scans from one or more files, no sample structure yet | `Spectra` |
| Multiple raw files that must stay paired with sample metadata | `MsExperiment` |
| A finished feature-by-sample matrix (metabolomics, or one level of proteomics) | `SummarizedExperiment` |
| A PSM-to-protein hierarchy that must stay traceable across aggregation | `QFeatures` |

## Best Practices and Troubleshooting

### Memory Management

```{r}
#| eval: false
# Check memory usage of Spectra object
object.size(ms_data) / 1e6  # Size in MB

# Convert to memory-efficient backend for large datasets
ms_data_hdf5 <- setBackend(ms_data, backend = MsBackendHdf5Peaks())

# Remove large objects when no longer needed
rm(ms_data_hdf5)
gc()  # Force garbage collection
```

### Common Issues and Solutions

| Issue | Symptom | Solution |
|-------|---------|----------|
| **mzR compilation fails** | Error installing MsBackendMzR | Install system dependencies: `libnetcdf-dev`, `libxml2-dev` |
| **Out of memory** | R crashes or slows down | Use HDF5 or SQL backend instead of in-memory |
| **Slow file reading** | `Spectra()` takes minutes | Use `backend = MsBackendHdf5Peaks()` for faster access |
| **Missing precursor info** | `precursorMz` returns NA | Check if file contains MS2 spectra with `any(msLevel(ms_data) == 2)` |
