29  Build Reproducible MS Reports

  • Show All Code
  • Hide All Code
  • View Source

A finished analysis is not a private folder of scripts on a local hard drive. It is a literate, executable document that a reviewer or collaborator can re-execute from raw data with a single command, accompanied by a public data deposition conforming to FAIR principles.

Throughout this book, we have moved from raw mass spectrometry spectra and chromatographic features (Parts I–II) through quantitative workflows, normalization, and statistical modeling (Parts III–V). However, computational mass spectrometry does not end with a p-value or an ROC curve.

A scientific finding is only as trustworthy as the computational pipeline that produced it. Without disciplined reporting and structured deposition, analyses suffer from computational drift: code breaks when software packages update, figures cannot be linked to the exact pipeline that generated them, and published tables cannot be audited or reused.

This chapter unites the reproducibility infrastructure established earlier in the book (renv, targets, Docker, Git) and directs it toward final dissemination: 1. Literate Parameterized Reporting: Developing parameterized Quarto reports that dynamically adapt across batches, biological contrasts, and threshold criteria. 2. Pipeline Integration: Coupling reports to targets directed acyclic graphs (DAGs) so documents read validated outputs without redundant recomputation. 3. The AI4SciFig Publication Design System: Authoring publication-grade figures conforming to strict international journal standards (Nature, Science, Cell). 4. Dynamic Publication Tables: Formatting publication-ready summary tables using gt and interactive exploration tables using DT. 5. FAIR Data Deposition: Depositing raw and processed data into ProteomeXchange (PRIDE, MassIVE) and MetaboLights according to international standards. 6. Continuous Integration (CI/CD): Automating validation and deployment using GitHub Actions.

WarningThe One Mistake to Avoid

Allowing the reporting document to recompute analytical steps. If your Quarto report runs peak picking, alignment, or statistical model fitting during rendering, it will eventually drift out of sync with your production pipeline, produce non-deterministic results, and mask expensive pipeline failures. The report reads validated artifacts—it never computes them.

29.1 Learning Objectives

By the end of this chapter you will be able to:

  • Construct parameterized Quarto templates (.qmd) and programmatically render batches of reports across multiple experimental conditions
  • Link reporting documents to an upstream targets pipeline via tarchetypes::tar_quarto() to guarantee cache validity
  • Formulate scientific visualizations adhering to the AI4SciFig publication standard: boxed 4-spine canvases, outward-facing ticks, perceptually uniform palettes, and exact physical print dimensions
  • Export publication-ready vector graphics (PDF/SVG) and 300+ dpi LZW-compressed raster images (TIFF)
  • Build publication tables using gt with scientific notation formatting, summary rows, and conditional styling
  • Structure proteomics metadata using the Sample and Data Relationship Format (SDRF) for ProteomeXchange/PRIDE deposition
  • Structure metabolomics metadata using the ISA-Tab and mzTab-M frameworks for MetaboLights deposition
  • Configure a GitHub Actions workflow to automate continuous integration and publication to GitHub Pages

29.2 Architectural Separation of Concerns

A production-grade mass spectrometry laboratory separates the analytical lifecycle into three distinct, decoupled tiers:

+-------------------------------------------------------------------------------+
|                      Three-Tier Reproducible MS Architecture                  |
+-------------------------------------------------------------------------------+
| 1. ENVIRONMENT TIER  | renv.lock, Dockerfile                                  |
|                      | Locks exact R packages, Bioconductor version, OS libs  |
|                      +--------------------------------------------------------+
| 2. COMPUTATION TIER  | targets DAG (_targets.R)                               |
|                      | Executes raw import, peak picking, normalization, DE   |
|                      +--------------------------------------------------------+
| 3. REPORTING TIER    | Quarto (.qmd), gt, AI4SciFig                           |
|                      | Reads cached targets, generates publication deliverables|
+-------------------------------------------------------------------------------+

The fundamental axiom of this architecture is: The report reads; the pipeline computes.

When computationally expensive operations (e.g., CentWave peak picking across 100 LC-MS runs or Monte Carlo power simulations) are embedded directly inside an R Markdown or Quarto file, rendering the document takes hours. If a single figure caption is edited, the entire document re-executes from scratch. By offloading computation to targets (Chapter 4), the report becomes an ultra-fast, read-only presentation layer.

29.3 Parameterized Quarto Reports for Reusable Workflows

A parameterized report uses a single Quarto template to generate customized deliverables depending on parameters passed at execution time. This enables automated batch reporting: generating per-sample QC summaries, analyzing multiple clinical centers, or conducting sensitivity analyses across varying FDR thresholds.

29.3.1 Declaring Parameters in the YAML Front Matter

Parameters are declared in the Quarto YAML header with default values:

---
title: "Differential Abundance Study Report"
author: "Lucas VHH TRAN"
date: today
format:
  html:
    theme: cosmo
    toc: true
    code-fold: true
params:
  study_accession: "PXD004886"
  contrast_name: "GroupA_vs_GroupB"
  fdr_cutoff: 0.05
  log2fc_cutoff: 1.0
  imputation_method: "MinProb"
execute:
  echo: false
  warning: false
  message: false
---

29.3.2 Accessing Parameters Programmatically

Within the document’s R code chunks, parameter values are accessed via the read-only params list:

Code 
# Accessing runtime parameters
cat("Processing Study:", params$study_accession, "\n")
cat("Significance Threshold: FDR <", params$fdr_cutoff, 
    "and |log2FC| >=", params$log2fc_cutoff, "\n")

# Filter pre-computed results using runtime parameters
significant_hits <- de_results %>%
  dplyr::filter(
    padj < params$fdr_cutoff,
    abs(log2FC) >= params$log2fc_cutoff
  )

29.3.3 Batch Rendering with purrr::walk

To generate an entire suite of reports across different analytical parameters or experimental cohorts, execute quarto::quarto_render() programmatically:

Code 
library(purrr)
library(quarto)

# Define experimental cohorts to report
cohorts <- c("Discovery_Berlin", "Validation_Prague", "External_Munich")

# Render an independent HTML report for each cohort
purrr::walk(cohorts, function(cohort) {
  quarto::quarto_render(
    input          = "templates/cohort_report.qmd",
    execute_params = list(cohort_name = cohort, fdr_cutoff = 0.01),
    output_file    = paste0("report_", cohort, ".html")
  )
})

29.4 Coupling Quarto Reports to targets DAGs

To guarantee that a reporting document reflects the latest data without manual re-rendering, integrate the Quarto file into your _targets.R pipeline using tarchetypes::tar_quarto().

# _targets.R
library(targets)
library(tarchetypes)

# Pipeline definition
list(
  # 1. Raw data import and filtering
  tar_target(raw_file_paths, list_raw_mzml("data/raw")),
  tar_target(raw_spectra, import_spectra(raw_file_paths)),
  
  # 2. Preprocessing & Normalization
  tar_target(feature_matrix, extract_features(raw_spectra)),
  tar_target(norm_matrix, normalize_vsn(feature_matrix)),
  
  # 3. Statistical Modeling
  tar_target(de_models, fit_limma(norm_matrix)),
  tar_target(de_summary, extract_top_table(de_models, fdr = 0.05)),
  
  # 4. Automated Literate Report
  tarchetypes::tar_quarto(
    report,
    path = "reports/final_manuscript_report.qmd"
  )
)

Inside final_manuscript_report.qmd, access pre-computed, validated pipeline nodes using targets::tar_read():

Code 
# Inside reports/final_manuscript_report.qmd
library(targets)

# Read validated pipeline targets from storage cache
norm_data  <- targets::tar_read(norm_matrix)
de_results <- targets::tar_read(de_summary)

If upstream raw files or normalization parameters change, targets detects the invalidated hash and re-renders the report. If nothing has changed, tar_make() skips the report entirely, saving substantial computational time.

29.5 The AI4SciFig Publication Design System

Scientific journals have exact layout and typography specifications. A standard ggplot2 plot with a grey background, default margins, and unconstrained fonts will be rejected by production editors or rendered illegibly when scaled to print columns.

The AI4SciFig design standard guarantees that figures comply with publication requirements:

+-------------------------------------------------------------------------------+
|                       AI4SciFig Design Standard Specifications                |
+-------------------------------------------------------------------------------+
| 1. CANVAS BOUNDARY   | Complete 4-spine boxed frame (black linewidth = 0.5 pt)|
| 2. TICK MARKS        | Outward-pointing tick marks (length = -2.5 pt)         |
| 3. TYPOGRAPHY        | Clean sans-serif (Arial/Helvetica); base font 7-7.5 pt |
| 4. PALETTES          | Okabe-Ito / Viridis (colorblind-safe, non-rainbow)     |
| 5. PRINT SCALING     | Sized to journal column widths: 88 mm, 120 mm, 180 mm  |
+-------------------------------------------------------------------------------+

29.5.1 Implementing theme_scifig in ggplot2

Code 
library(ggplot2)

theme_scifig <- function(base_size = 7.5, base_family = "sans") {
  theme_bw(base_size = base_size, base_family = base_family) +
    theme(
      # Complete 4-spine enclosed border
      panel.border       = element_rect(colour = "#111111", fill = NA, linewidth = 0.55),
      panel.grid.major   = element_blank(),
      panel.grid.minor   = element_blank(),
      
      # Directional outward-facing tick marks
      axis.ticks         = element_line(colour = "#111111", linewidth = 0.45),
      axis.ticks.length  = unit(-2.5, "pt"),
      
      # Typography and padding
      axis.title.x       = element_text(size = base_size, face = "bold", margin = margin(t = 4)),
      axis.title.y       = element_text(size = base_size, face = "bold", margin = margin(r = 4)),
      axis.text.x        = element_text(size = base_size - 0.5, colour = "#222222", margin = margin(t = 3)),
      axis.text.y        = element_text(size = base_size - 0.5, colour = "#222222", margin = margin(r = 3)),
      
      # Legend positioning
      legend.background  = element_blank(),
      legend.key         = element_blank(),
      legend.title       = element_text(size = base_size - 0.5, face = "bold"),
      legend.text        = element_text(size = base_size - 1.0),
      
      # Strip headers for faceted panels
      strip.background   = element_rect(colour = "#111111", fill = "#EFEFEF", linewidth = 0.55),
      strip.text         = element_text(size = base_size - 0.5, face = "bold"),
      plot.title         = element_text(size = base_size + 1.0, face = "bold", hjust = 0),
      plot.margin        = margin(4, 4, 4, 4, "mm")
    )
}

29.5.2 Publication Figure Export Standards

When exporting graphics for submission: 1. Line Plots, Scatterplots, and Bar Charts: Export as vector formats (.pdf or .svg). Vector graphics remain crisp at any magnification and allow editors to edit typography. 2. Heatmaps and High-Density Scans: Export as raster formats (.tiff or .png) at \ge 300\text{ dpi} with LZW compression to prevent multi-megabyte file sizes. 3. Exact Dimensions: Size directly in millimeters using journal column widths: - Single column: 88\text{ mm} (3.46\text{ in}) - 1.5 column: 120\text{ mm} (4.72\text{ in}) - Double column (full page width): 180\text{ mm} (7.08\text{ in})

Code 
# Exporting vector PDF for journal submission (single-column width = 88 mm)
ggplot2::ggsave(
  filename = "figures/volcano_publication.pdf",
  plot     = volcano_plot,
  width    = 88, 
  height   = 88, 
  units    = "mm",
  device   = cairo_pdf
)

# Exporting 300-dpi LZW-compressed TIFF raster
ggplot2::ggsave(
  filename    = "figures/volcano_publication.tiff",
  plot        = volcano_plot,
  width       = 88, 
  height      = 88, 
  units       = "mm", 
  dpi         = 300, 
  compression = "lzw"
)

29.6 Dynamic Scientific Tables with gt and DT

Scientific manuscripts require two categories of tables: - Static Publication Tables: High-aesthetic, formatted tables summarizing top statistical findings, printed in the main text. - Interactive Supplementary Tables: Searchable, downloadable tables containing all thousands of quantified features, intended for reviewers and online readers.

29.7 Depositing Data: The FAIR Principles

The FAIR principles dictate that research data must be Findable, Accessible, Interoperable, and Reusable (Wilkinson et al. 2016). Major scientific publishers and funding agencies mandate deposition in community-recognized repositories before manuscript acceptance.

+-------------------------------------------------------------------------------+
|                       Community Repositories for MS Data                      |
+-------------------------------------------------------------------------------+
| PROTEOMICS     | PRIDE / MassIVE (ProteomeXchange consortium)                 |
|                | Formats: Raw files, mzML, mzIdentML (.mzid), SDRF metadata   |
|                +--------------------------------------------------------------+
| METABOLOMICS   | MetaboLights / Metabolomics Workbench                        |
|                | Formats: Raw files, mzML, ISA-Tab metadata, mzTab-M          |
|                +--------------------------------------------------------------+
| CODE & TABLES  | Zenodo / Figshare / Software Heritage                        |
|                | Formats: renv.lock, _targets.R, Dockerfile (Citable DOI)     |
+-------------------------------------------------------------------------------+

29.7.1 Proteomics: A ProteomeXchange / PRIDE Submission

A complete ProteomeXchange submission via the PRIDE Submission Tool (px-submission-tool) requires:

  1. Raw Spectral Files: Native instrument vendor files (.raw, .wiff, .d) along with standard open centroided .mzML files.
  2. Identification Evidence: The peptide-spectrum matching results in standard mzIdentML (.mzid) format.
  3. Quantification Matrices: Normalized feature and protein intensity tables in mzTab format.
  4. Experimental Metadata (SDRF-Proteomics): The Sample and Data Relationship Format (sdrf.tsv), an open tab-delimited standard mapping raw files to biological characteristics:
source name characteristics[organism] characteristics[disease] comment[data file] comment[fraction identifier]
Sample_01 Homo sapiens Healthy Control Run01.raw 1
Sample_02 Homo sapiens Vasculitis Active Run02.raw 1

The Bioconductor package rpx allows programmatic querying and downloading of deposited ProteomeXchange accessions:

Code 
library(rpx)

# Query public PRIDE dataset
px <- rpx::PXDataset("PXD004886")
cat("PRIDE Accession:", pxid(px), "\n")
cat("Deposited Files:", length(pxfiles(px)), "\n")
head(pxfiles(px), 5)

29.7.2 Metabolomics: A MetaboLights Submission

MetaboLights organizes datasets under the ISA-Tab standard (Investigation, Study, Assay):

  1. i_Investigation.txt: Top-level study metadata, experimental design, and contact information.
  2. s_Study.txt: Biological sample characteristics (organism, tissue, clinical covariates).
  3. a_Assay.txt: Analytical assay parameters (chromatography column, solvent gradients, mass analyzer parameters, scan polarity).
  4. m_metabolite.tsv: The final metabolite identification table, cross-referencing features to HMDB/ChEBI identifiers and MSI confidence levels (Chapter 9).

29.8 Continuous Integration & Deployment (CI/CD)

To ensure that your Quarto manuscript, web documentation, and book render cleanly without manual local execution, configure a GitHub Actions CI/CD pipeline.

Create .github/workflows/deploy.yml in your repository:

name: Render and Deploy Quarto Book

on:
  push:
    branches: [ master, main ]
  workflow_dispatch:

jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up R
        uses: r-lib/actions/setup-r@v2
        with:
          r-version: '4.4.1'
          use-public-rspm: true

      - name: Set up Quarto
        uses: quarto-dev/quarto-actions/setup@v2

      - name: Restore R package cache
        uses: actions/cache@v4
        with:
          path: ~/.local/share/renv
          key: ${{ runner.os }}-renv-${{ hashFiles('**/renv.lock') }}
          restore-keys: |
            ${{ runner.os }}-renv-

      - name: Restore renv dependencies
        run: |
          Rscript -e "install.packages('renv')"
          Rscript -e "renv::restore()"

      - name: Render Quarto Project
        run: quarto render

      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./docs

Whenever commits are pushed, GitHub Actions spawns an isolated runner, installs the locked packages from renv.lock, renders all chapters, and pushes the compiled HTML assets to GitHub Pages.

29.9 Pre-Publication Reporting Checklist

Before submitting a manuscript or uploading supplementary deliverables, verify each item:

29.10 Summary

  • Reproducible reporting bridges computational bioinformatics and peer-reviewed scientific literature.
  • Parameterized Quarto reports allow dynamic multi-batch and multi-cohort analysis from a single template.
  • Integrating reports with targets ensures reports re-render only when upstream dependencies change, preventing code drift.
  • The AI4SciFig standard guarantees that figures satisfy high-impact journal requirements: 4-spine boxed borders, outward ticks, colorblind-safe palettes, and millimeter print scaling.
  • Scientific tables require a dual strategy: styled gt summaries for print manuscripts and searchable DT tables for supplementary materials.
  • Adhering to FAIR principles via PRIDE, MetaboLights, and Zenodo ensures that your mass spectrometry findings can be audited, validated, and reused by the scientific community.

29.11 Exercises

  1. Parameterization Challenge: Create a parameterized Quarto document that accepts significance_alpha and log2fc_min as parameters. Render the document twice from the command line: once with standard discovery settings (\alpha = 0.05, \text{FC} \ge 1.0) and once with stringent verification settings (\alpha = 0.01, \text{FC} \ge 2.0). Confirm that the exported table rows adjust dynamically.
  2. AI4SciFig Styling: Take a default ggplot2 scatterplot and refactor it using theme_scifig(). Export it at 88\text{ mm} \times 88\text{ mm} as a vector PDF using cairo_pdf. Open the resulting file and verify that text remains editable and legible at 100\% print zoom.
  3. Table Formatting: Using gt, format a table of top 10 metabolite features. Include:
    • Formatted m/z values with 4 decimal places
    • Retention times formatted to 2 decimal places
    • Raw p-values in scientific notation (1.20 \times 10^{-4})
    • A footnote explaining the multiple testing correction applied
  4. SDRF Creation: Download an example SDRF template from the ProteomeXchange consortium. Construct a valid 10-row SDRF table mapping 5 control and 5 disease raw files to their biological metadata, instrument model, and sample state.
  5. CI/CD Configuration: Draft a GitHub Actions YAML workflow that installs Bioconductor packages and renders your report upon pushing to GitHub. What cache directories must be preserved to avoid reinstalling Bioconductor dependencies on every commit?

# Build Reproducible MS Reports

> *A finished analysis is not a private folder of scripts on a local hard drive. It is a literate, executable document that a reviewer or collaborator can re-execute from raw data with a single command, accompanied by a public data deposition conforming to FAIR principles.*

Throughout this book, we have moved from raw mass spectrometry spectra and chromatographic features (Parts I–II) through quantitative workflows, normalization, and statistical modeling (Parts III–V). However, computational mass spectrometry does not end with a $p$-value or an ROC curve. 

A scientific finding is only as trustworthy as the computational pipeline that produced it. Without disciplined reporting and structured deposition, analyses suffer from computational drift: code breaks when software packages update, figures cannot be linked to the exact pipeline that generated them, and published tables cannot be audited or reused.

This chapter unites the reproducibility infrastructure established earlier in the book (`renv`, `targets`, Docker, Git) and directs it toward final dissemination:
1. **Literate Parameterized Reporting**: Developing parameterized Quarto reports that dynamically adapt across batches, biological contrasts, and threshold criteria.
2. **Pipeline Integration**: Coupling reports to `targets` directed acyclic graphs (DAGs) so documents read validated outputs without redundant recomputation.
3. **The AI4SciFig Publication Design System**: Authoring publication-grade figures conforming to strict international journal standards (*Nature*, *Science*, *Cell*).
4. **Dynamic Publication Tables**: Formatting publication-ready summary tables using `gt` and interactive exploration tables using `DT`.
5. **FAIR Data Deposition**: Depositing raw and processed data into ProteomeXchange (PRIDE, MassIVE) and MetaboLights according to international standards.
6. **Continuous Integration (CI/CD)**: Automating validation and deployment using GitHub Actions.

::: {.callout-warning title="The One Mistake to Avoid"}
Allowing the reporting document to recompute analytical steps. If your Quarto report runs peak picking, alignment, or statistical model fitting during rendering, it will eventually drift out of sync with your production pipeline, produce non-deterministic results, and mask expensive pipeline failures. The report reads validated artifacts—it never computes them.
:::

## Learning Objectives

By the end of this chapter you will be able to:

- Construct parameterized Quarto templates (`.qmd`) and programmatically render batches of reports across multiple experimental conditions
- Link reporting documents to an upstream `targets` pipeline via `tarchetypes::tar_quarto()` to guarantee cache validity

- Structure metabolomics metadata using the ISA-Tab and mzTab-M frameworks for MetaboLights deposition
- Configure a GitHub Actions workflow to automate continuous integration and publication to GitHub Pages

## Architectural Separation of Concerns

A production-grade mass spectrometry laboratory separates the analytical lifecycle into three distinct, decoupled tiers:

```
+-------------------------------------------------------------------------------+
|                      Three-Tier Reproducible MS Architecture                  |
+-------------------------------------------------------------------------------+
| 1. ENVIRONMENT TIER  | renv.lock, Dockerfile                                  |
|                      | Locks exact R packages, Bioconductor version, OS libs  |
|                      +--------------------------------------------------------+
| 2. COMPUTATION TIER  | targets DAG (_targets.R)                               |
|                      | Executes raw import, peak picking, normalization, DE   |
|                      +--------------------------------------------------------+
| 3. REPORTING TIER    | Quarto (.qmd), gt, AI4SciFig                           |
|                      | Reads cached targets, generates publication deliverables|
+-------------------------------------------------------------------------------+
```

The fundamental axiom of this architecture is: **The report reads; the pipeline computes.** 

When computationally expensive operations (e.g., CentWave peak picking across 100 LC-MS runs or Monte Carlo power simulations) are embedded directly inside an R Markdown or Quarto file, rendering the document takes hours. If a single figure caption is edited, the entire document re-executes from scratch. By offloading computation to `targets` (Chapter 4), the report becomes an ultra-fast, read-only presentation layer.

## Parameterized Quarto Reports for Reusable Workflows

A **parameterized report** uses a single Quarto template to generate customized deliverables depending on parameters passed at execution time. This enables automated batch reporting: generating per-sample QC summaries, analyzing multiple clinical centers, or conducting sensitivity analyses across varying FDR thresholds.

### Declaring Parameters in the YAML Front Matter

Parameters are declared in the Quarto YAML header with default values:

```yaml
---
title: "Differential Abundance Study Report"
author: "Lucas VHH TRAN"
date: today
format:
  html:
    theme: cosmo
    toc: true
    code-fold: true
params:
  study_accession: "PXD004886"
  contrast_name: "GroupA_vs_GroupB"
  fdr_cutoff: 0.05
  log2fc_cutoff: 1.0
  imputation_method: "MinProb"
execute:
  echo: false
  warning: false
  message: false
---
```

### Accessing Parameters Programmatically

Within the document's R code chunks, parameter values are accessed via the read-only `params` list:

```{r}
#| eval: false
# Accessing runtime parameters
cat("Processing Study:", params$study_accession, "\n")
cat("Significance Threshold: FDR <", params$fdr_cutoff, 
    "and |log2FC| >=", params$log2fc_cutoff, "\n")

# Filter pre-computed results using runtime parameters
significant_hits <- de_results %>%
  dplyr::filter(
    padj < params$fdr_cutoff,
    abs(log2FC) >= params$log2fc_cutoff
  )
```

### Batch Rendering with `purrr::walk`

To generate an entire suite of reports across different analytical parameters or experimental cohorts, execute `quarto::quarto_render()` programmatically:

```{r}
#| eval: false
library(purrr)
library(quarto)

# Define experimental cohorts to report
cohorts <- c("Discovery_Berlin", "Validation_Prague", "External_Munich")

# Render an independent HTML report for each cohort
purrr::walk(cohorts, function(cohort) {
  quarto::quarto_render(
    input          = "templates/cohort_report.qmd",
    execute_params = list(cohort_name = cohort, fdr_cutoff = 0.01),
    output_file    = paste0("report_", cohort, ".html")
  )
})
```

## Coupling Quarto Reports to `targets` DAGs

To guarantee that a reporting document reflects the latest data without manual re-rendering, integrate the Quarto file into your `_targets.R` pipeline using `tarchetypes::tar_quarto()`.

```r
# _targets.R
library(targets)
library(tarchetypes)

# Pipeline definition
list(
  # 1. Raw data import and filtering
  tar_target(raw_file_paths, list_raw_mzml("data/raw")),
  tar_target(raw_spectra, import_spectra(raw_file_paths)),
  
  # 2. Preprocessing & Normalization
  tar_target(feature_matrix, extract_features(raw_spectra)),
  tar_target(norm_matrix, normalize_vsn(feature_matrix)),
  
  # 3. Statistical Modeling
  tar_target(de_models, fit_limma(norm_matrix)),
  tar_target(de_summary, extract_top_table(de_models, fdr = 0.05)),
  
  # 4. Automated Literate Report
  tarchetypes::tar_quarto(
    report,
    path = "reports/final_manuscript_report.qmd"
  )
)
```

Inside `final_manuscript_report.qmd`, access pre-computed, validated pipeline nodes using `targets::tar_read()`:

```{r}
#| eval: false
# Inside reports/final_manuscript_report.qmd
library(targets)

# Read validated pipeline targets from storage cache
norm_data  <- targets::tar_read(norm_matrix)
de_results <- targets::tar_read(de_summary)
```

If upstream raw files or normalization parameters change, `targets` detects the invalidated hash and re-renders the report. If nothing has changed, `tar_make()` skips the report entirely, saving substantial computational time.

## The AI4SciFig Publication Design System

Scientific journals have exact layout and typography specifications. A standard ggplot2 plot with a grey background, default margins, and unconstrained fonts will be rejected by production editors or rendered illegibly when scaled to print columns.

The **AI4SciFig** design standard guarantees that figures comply with publication requirements:

```
+-------------------------------------------------------------------------------+
|                       AI4SciFig Design Standard Specifications                |
+-------------------------------------------------------------------------------+
| 1. CANVAS BOUNDARY   | Complete 4-spine boxed frame (black linewidth = 0.5 pt)|
| 2. TICK MARKS        | Outward-pointing tick marks (length = -2.5 pt)         |
| 3. TYPOGRAPHY        | Clean sans-serif (Arial/Helvetica); base font 7-7.5 pt |
| 4. PALETTES          | Okabe-Ito / Viridis (colorblind-safe, non-rainbow)     |
| 5. PRINT SCALING     | Sized to journal column widths: 88 mm, 120 mm, 180 mm  |
+-------------------------------------------------------------------------------+
```

### Implementing `theme_scifig` in ggplot2

```{r}
#| eval: true
#| echo: true
library(ggplot2)

theme_scifig <- function(base_size = 7.5, base_family = "sans") {
  theme_bw(base_size = base_size, base_family = base_family) +
    theme(
      # Complete 4-spine enclosed border
      panel.border       = element_rect(colour = "#111111", fill = NA, linewidth = 0.55),
      panel.grid.major   = element_blank(),
      panel.grid.minor   = element_blank(),
      
      # Directional outward-facing tick marks
      axis.ticks         = element_line(colour = "#111111", linewidth = 0.45),
      axis.ticks.length  = unit(-2.5, "pt"),
      
      # Typography and padding
      axis.title.x       = element_text(size = base_size, face = "bold", margin = margin(t = 4)),
      axis.title.y       = element_text(size = base_size, face = "bold", margin = margin(r = 4)),
      axis.text.x        = element_text(size = base_size - 0.5, colour = "#222222", margin = margin(t = 3)),
      axis.text.y        = element_text(size = base_size - 0.5, colour = "#222222", margin = margin(r = 3)),
      
      # Legend positioning
      legend.background  = element_blank(),
      legend.key         = element_blank(),
      legend.title       = element_text(size = base_size - 0.5, face = "bold"),
      legend.text        = element_text(size = base_size - 1.0),
      
      # Strip headers for faceted panels
      strip.background   = element_rect(colour = "#111111", fill = "#EFEFEF", linewidth = 0.55),
      strip.text         = element_text(size = base_size - 0.5, face = "bold"),
      plot.title         = element_text(size = base_size + 1.0, face = "bold", hjust = 0),
      plot.margin        = margin(4, 4, 4, 4, "mm")
    )
}
```

### Publication Figure Export Standards

When exporting graphics for submission:
1. **Line Plots, Scatterplots, and Bar Charts**: Export as **vector formats** (`.pdf` or `.svg`). Vector graphics remain crisp at any magnification and allow editors to edit typography.
2. **Heatmaps and High-Density Scans**: Export as **raster formats** (`.tiff` or `.png`) at $\ge 300\text{ dpi}$ with LZW compression to prevent multi-megabyte file sizes.
3. **Exact Dimensions**: Size directly in millimeters using journal column widths:
   - **Single column**: $88\text{ mm}$ ($3.46\text{ in}$)
   - **1.5 column**: $120\text{ mm}$ ($4.72\text{ in}$)
   - **Double column (full page width)**: $180\text{ mm}$ ($7.08\text{ in}$)

```{r}
#| eval: false
# Exporting vector PDF for journal submission (single-column width = 88 mm)
ggplot2::ggsave(
  filename = "figures/volcano_publication.pdf",
  plot     = volcano_plot,
  width    = 88, 
  height   = 88, 
  units    = "mm",
  device   = cairo_pdf
)

# Exporting 300-dpi LZW-compressed TIFF raster
ggplot2::ggsave(
  filename    = "figures/volcano_publication.tiff",
  plot        = volcano_plot,
  width       = 88, 
  height      = 88, 
  units       = "mm", 
  dpi         = 300, 
  compression = "lzw"
)
```

## Dynamic Scientific Tables with `gt` and `DT`

Scientific manuscripts require two categories of tables:
- **Static Publication Tables**: High-aesthetic, formatted tables summarizing top statistical findings, printed in the main text.
- **Interactive Supplementary Tables**: Searchable, downloadable tables containing all thousands of quantified features, intended for reviewers and online readers.

## Depositing Data: The FAIR Principles

The **FAIR principles** dictate that research data must be **F**indable, **A**ccessible, **I**nteroperable, and **R**eusable [@wilkinson2016fair]. Major scientific publishers and funding agencies mandate deposition in community-recognized repositories before manuscript acceptance.

```
+-------------------------------------------------------------------------------+
|                       Community Repositories for MS Data                      |
+-------------------------------------------------------------------------------+
| PROTEOMICS     | PRIDE / MassIVE (ProteomeXchange consortium)                 |
|                | Formats: Raw files, mzML, mzIdentML (.mzid), SDRF metadata   |
|                +--------------------------------------------------------------+
| METABOLOMICS   | MetaboLights / Metabolomics Workbench                        |
|                | Formats: Raw files, mzML, ISA-Tab metadata, mzTab-M          |
|                +--------------------------------------------------------------+
| CODE & TABLES  | Zenodo / Figshare / Software Heritage                        |
|                | Formats: renv.lock, _targets.R, Dockerfile (Citable DOI)     |
+-------------------------------------------------------------------------------+
```

### Proteomics: A ProteomeXchange / PRIDE Submission

A complete ProteomeXchange submission via the PRIDE Submission Tool (`px-submission-tool`) requires:

1. **Raw Spectral Files**: Native instrument vendor files (`.raw`, `.wiff`, `.d`) along with standard open centroided `.mzML` files.
2. **Identification Evidence**: The peptide-spectrum matching results in standard `mzIdentML` (`.mzid`) format.
3. **Quantification Matrices**: Normalized feature and protein intensity tables in `mzTab` format.
4. **Experimental Metadata (SDRF-Proteomics)**: The Sample and Data Relationship Format (`sdrf.tsv`), an open tab-delimited standard mapping raw files to biological characteristics:

| source name | characteristics[organism] | characteristics[disease] | comment[data file] | comment[fraction identifier] |
|:---|:---|:---|:---|:---|
| Sample_01 | *Homo sapiens* | Healthy Control | `Run01.raw` | 1 |
| Sample_02 | *Homo sapiens* | Vasculitis Active | `Run02.raw` | 1 |

The Bioconductor package `rpx` allows programmatic querying and downloading of deposited ProteomeXchange accessions:

```{r}
#| eval: false
library(rpx)

# Query public PRIDE dataset
px <- rpx::PXDataset("PXD004886")
cat("PRIDE Accession:", pxid(px), "\n")
cat("Deposited Files:", length(pxfiles(px)), "\n")
head(pxfiles(px), 5)
```

### Metabolomics: A MetaboLights Submission

MetaboLights organizes datasets under the **ISA-Tab** standard (Investigation, Study, Assay):

1. **`i_Investigation.txt`**: Top-level study metadata, experimental design, and contact information.
2. **`s_Study.txt`**: Biological sample characteristics (organism, tissue, clinical covariates).
3. **`a_Assay.txt`**: Analytical assay parameters (chromatography column, solvent gradients, mass analyzer parameters, scan polarity).
4. **`m_metabolite.tsv`**: The final metabolite identification table, cross-referencing features to HMDB/ChEBI identifiers and MSI confidence levels (Chapter 9).

## Continuous Integration & Deployment (CI/CD)

To ensure that your Quarto manuscript, web documentation, and book render cleanly without manual local execution, configure a **GitHub Actions** CI/CD pipeline.

Create `.github/workflows/deploy.yml` in your repository:

```yaml
name: Render and Deploy Quarto Book

on:
  push:
    branches: [ master, main ]
  workflow_dispatch:

jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up R
        uses: r-lib/actions/setup-r@v2
        with:
          r-version: '4.4.1'
          use-public-rspm: true

      - name: Set up Quarto
        uses: quarto-dev/quarto-actions/setup@v2

      - name: Restore R package cache
        uses: actions/cache@v4
        with:
          path: ~/.local/share/renv
          key: ${{ runner.os }}-renv-${{ hashFiles('**/renv.lock') }}
          restore-keys: |
            ${{ runner.os }}-renv-

      - name: Restore renv dependencies
        run: |
          Rscript -e "install.packages('renv')"
          Rscript -e "renv::restore()"

      - name: Render Quarto Project
        run: quarto render

      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v3
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./docs
```

Whenever commits are pushed, GitHub Actions spawns an isolated runner, installs the locked packages from `renv.lock`, renders all chapters, and pushes the compiled HTML assets to GitHub Pages.

## Pre-Publication Reporting Checklist

Before submitting a manuscript or uploading supplementary deliverables, verify each item:

- [ ] **Decoupled Architecture**: All computationally intensive models are executed in `targets` or standalone scripts; Quarto reports only read validated outputs.
- [ ] **Exact Dimensions**: Figures are exported to physical journal print dimensions ($88\text{ mm}$ or $180\text{ mm}$) with fonts sized between $7.0\text{ pt}$ and $8.5\text{ pt}$.
- [ ] **Vector Art**: Plots, diagrams, and ROC curves are exported as vector PDFs or SVGs; heatmaps are exported as 300+ dpi LZW-compressed TIFFs.
- [ ] **Accessible Palettes**: All figures use colorblind-safe color schemes (Okabe-Ito, Viridis); no figures encode data solely through red/green contrast.
- [ ] **Tidy Machine-Readable Tables**: Numerical results are exported as structured CSV files alongside formatted static tables.
- [ ] **Repository Submission**: Raw data and search outputs are uploaded to PRIDE or MetaboLights, and private reviewer access tokens are generated.
- [ ] **Code Provenance**: Analysis scripts, `renv.lock`, and Dockerfiles are deposited on Zenodo with a minted DOI cited in the manuscript's Data Availability statement.
- [ ] **Session Information Captured**: `sessionInfo()` or `sessioninfo::session_info()` is appended to all reporting documents.

## Summary

- Reproducible reporting bridges computational bioinformatics and peer-reviewed scientific literature.
- **Parameterized Quarto reports** allow dynamic multi-batch and multi-cohort analysis from a single template.
- Integrating reports with **`targets`** ensures reports re-render only when upstream dependencies change, preventing code drift.
- The **AI4SciFig standard** guarantees that figures satisfy high-impact journal requirements: 4-spine boxed borders, outward ticks, colorblind-safe palettes, and millimeter print scaling.
- Scientific tables require a dual strategy: styled **`gt`** summaries for print manuscripts and searchable **`DT`** tables for supplementary materials.
- Adhering to **FAIR principles** via PRIDE, MetaboLights, and Zenodo ensures that your mass spectrometry findings can be audited, validated, and reused by the scientific community.
